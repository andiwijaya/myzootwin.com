# M1-07 — Editing, removal and bounded refunds

Status: COMPLETE locally, 2026-10-31 UTC. Implementation/evidence commit: 774f5ba639936039db73d8101a95dcec47f754bb (local only). Production has not been pushed or deployed.

Selecting a constructed path or habitat exposes **Remove selected object**. A native modal names the object, explains the consequence and exact refund, focuses **Keep object** first, traps keyboard focus and pauses the renderer/simulation. Cancel or native Escape leaves authoritative data unchanged. Confirm commits one revision-checked removal; repeated/stale confirmation cannot remove a later replacement. Removed occupancy, catalog identities, selection/ghosts and derived viewing routes update together. Original gate path and scenery are protected; referenced animals/facilities or active visitor routes prevent removal rather than orphaning future data.

**Undo last removal** restores the original placement and recalculates access. It survives preview close/reopen, renderer remount/retry in the same page through a cloned, bounded one-operation memento. A successful later world edit/build invalidates it; failed/cancelled operations do not. Correcting a misplaced object means removing it and building again at a valid location. There is no direct Move tool. A full page reload still resets this preview; player autosave/Continue remains M5.

## Refund decision grounded in the PRD

The exact M1-07 item requires select/delete/correct according to refund rules and consistent balance/occupancy. Section 4.6 permits limited refund/recovery, but specifies **no percentage or sale price**. Current M1 construction has never charged coins, so its actual refund is **0 ZC**, with no credit ledger entry and no coin change. There is no fabricated income or unlimited-money mode.

The tested transaction contract can refund at most the real build debit attributed to that object, less prior active refunds. It recomputes the amount from authoritative ledger entries, ignoring a caller's displayed amount. A refund references its original purchase; Undo uses a negative `restore` entry referencing that exact refund. Restore cannot exceed the refund or overdraw the current balance. Save validation checks chronological, unique, reconciled references/caps. Thus a free rebuild cannot resell an already refunded purchase, and repeated remove/Undo cycles cannot mint coins. Synthetic paid fixtures use finite balances and expenses; they do not enable player pricing or complete M3. Actual costs/refund balancing remain M3 configuration work.

World/ledger/currency changes are prepared and schema-validated before atomic commit. Undo restores world data only and appends the required exact debit; it does not roll back elapsed time, animal state, missions or unrelated money. World mismatch or insufficient funds rejects without partial changes. Runtime Undo is plain cloned data, outside the player save contract; no mesh/DOM/storage references.
